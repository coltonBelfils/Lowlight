# Lowlight Spec Critique (Draft v0.1)

This is a critique of [SPECIFICATION.md](../../SPECIFICATION.md). Section 1 covers the six structural problems that affect several features at once. Section 2 goes through the spec section by section. Section 3 lists the decisions I think you need to make first.

---

## 1. Structural Concerns (fix these first)

### A. References have no lifetime story
The spec says "Rust-like ownership," but it never says how long a borrow lives. That leaves these open:
- Can a function return a reference? (`(s &string) &string` — which input does the result borrow from?)
- Can a struct store a reference?
- When does a borrow end? At the end of the scope, or at its last use?

You have roughly three options:
1. **Rust-style lifetime annotations.** Very expressive, but heavy.
2. **Second-class references.** References can only be parameters or locals, and can never be returned or stored (the approach Hylo/Val takes). This is much simpler and fits your "transparent" goal.
3. **Elision rules only.** No annotations; the compiler infers lifetimes from fixed rules. It works until a case needs an annotation and you have none to offer.

The borrowing section can't really be written until you pick one.

There is also a contradiction in [§5.2](../specification/v0.1_SPECIFICATION.md#L130-L137). It says `&-` is **mandatory at the call site**, but method calls auto-borrow with no annotation: `pt.translate(5, 5)` ([L306](../specification/v0.1_SPECIFICATION.md#L306)), `v.push(4)`, `cache.insert(...)`. Either methods are an exception or the rule needs rewording. **Reborrowing** is also unspecified: inside `push`, `list` is already a `&-[int]`. Does passing it on to a helper need `&-list`, and does that produce a `&-&-[int]`?

### B. Newlines as separators in an expression language
[§2.1](../specification/v0.1_SPECIFICATION.md#L22-L28) gives the rule but none of the edge cases. In an expression-oriented language those edge cases come up everywhere:
```
let x = a
    - b              // one expression (a - b), or two (`a`, then `-b`)?

if (c) { 1 }
else { 2 }           // does the newline end the `if`?

let r = items
    .filter(...)     // is a leading `.` a continuation?
```
You also need to say whether newlines are ignored inside `()` and `[]`. The trailing-comma rule in §7.3 implies they are, but the spec never says so. Go's rule is a proven model: insert a separator only after a line that ends in an identifier, a literal, a closing bracket, or certain keywords.

### C. `match` has no terminator
Because `match` is "container-free" ([§12](../specification/v0.1_SPECIFICATION.md#L416-L437)), nested matches have the dangling-else problem:
```
match (a)
    when 1: match (b)
        when true: "x"
        else: "y"        // inner match or outer?
    else: "z"
```
A match that is exhaustive without an `else` (every enum variant covered) has no visible end at all. And if `else` is required as the terminator, the enum example's `else: 0.0` is unreachable code that the language would force you to write. Your options are to require braces around the arms (bending the `{}` rule), add an `end` keyword, or use indentation.

### D. Two optional systems at once
The spec has optionals tied to **names** (`user?`) and optionals tied to **types** (`?T` in [L153](../specification/v0.1_SPECIFICATION.md#L153) and [L217](../specification/v0.1_SPECIFICATION.md#L217)). Many optional values have no name at all: `ages["Alice"]`, `find_user(id)`, or a loop with no `else`. So it's unclear what the `?` suffix on a name actually guarantees. Open questions:
- **`let b = user?`**: is `b` a `bool` (a presence test, which is what `if (user?)` means) or the optional itself (which is what `first_even?` means at [L407](../specification/v0.1_SPECIFICATION.md#L407))? The same expression currently means two different things.
- **`if (flag?)`** where `flag` holds an optional `bool`: does it test presence or the value?
- **Are `user` and `user?` separate identifiers?** Can both be in scope at once?
- **Fields, parameters, return types.** Is it `email?: string`, `(u? User)`, `() ?User`?
- **Collections.** The elements of `[?int]` have no names to carry a `?`.
- **Nested optionals.** A lookup in `#[string: ?int]` gives `??int`. Is that flattened?
- **`user?.name`.** Is `?.` a chaining operator, or is it the identifier `user?` followed by `.name` with implicit chaining? What does `find_user(id)?.name` mean?
- **Narrowing.** Is narrowing undone if `user? = none` happens inside the `if`? Does it work for a guard like `if (!user?) { f <- none }` followed by `user.name`? For `&&` conditions? For fields such as `a.b?`?
- **Interpolation.** In `"Are you $ready?"`, the `?` gets swallowed into the identifier.

Suggestion: make `?T` the single source of truth. The name suffix can stay as a required marker that the compiler checks against the type. Or drop one of the two systems.

### E. `<-` and `&-`: lexing and semantics
- **Lexing:** `x<-5` and `x < -5` look the same. Under maximal munch (the lexer always takes the longest token it can), `if (x<-5)` becomes an unwind to a label named `x`. The same problem hits `a&-b` vs `a & -b` if `&` is also bitwise AND. You need a rule: required whitespace, or a different token.
- **"Immediate block":** does the body of a braceless `if` count as a block? Inside a loop, is `if (c) <- 5` a continue, or does it yield 5 from the `if`?
- **"Topmost `<-` in a `for` acts as continue":** continue with what value? You need a bare `<-` or a unit value.
- **`func_name <-`:**
  - Anonymous lambdas have no name to target.
  - A local variable could shadow the function's name.
  - Methods would need `Point.length <- x`.
  - The rule must say the target has to be **lexically enclosing**. Otherwise you get non-local returns across calls or closures, and in C that means `setjmp`/`longjmp`.
- **Temporaries:** in `f(make_string(), { g <- 1 })`, the string has already been built when the jump happens, so it has to be freed first.

### F. No unit type and no never type
Several things have no defined type:
- The body of `append_tag` ([L103](../specification/v0.1_SPECIFICATION.md#L103)).
- An assignment like `x = 20`.
- A `for` loop used as a statement.
- `for (true)` with no `else`. The rule makes it `?T`, but it never finishes normally.
- The `<-` expression itself. It needs to be a never type (one that matches any other type) so that `if (c) f <- 1 else 2` type-checks.

[§6.4](../specification/v0.1_SPECIFICATION.md#L174-L182) also talks about "statements without a value," which contradicts principle 3 ("everything is an expression").

## 2. Section-by-Section

### §1 Principles
- **"Zero hidden runtime overhead"** clashes with several features:
  - `let s = "Hello"` allocates on the heap ([L96](../specification/v0.1_SPECIFICATION.md#L96)).
  - Interpolation allocates.
  - An interface held by value (not by reference) needs a heap allocation.
- **"Explicit pointers"**: the language has no pointer type. A systems language that compiles to C needs raw pointers and a way to call C code (`extern`, `unsafe`).
- **"`[]` strictly reserved for data and types"**: `[]` is also used for indexing (`ages["Diana"]`) and for patterns (`Circle[r]`).

### §2 Lexical
- Not yet specified:
  - Block comments and doc comments.
  - Escape sequences.
  - Char literal syntax.
  - Numeric literal forms: hex/binary, `_` separators, type suffixes like `10u8`.

### §3 `let` / `bind`
- **Deep vs. shallow immutability is inconsistent, and the inconsistency leaks:**
  - `bind cache` allows `insert`, which needs a mutable borrow. Yet `bind pt` forbids `pt.translate`, which needs the same thing.
  - Under `bind`, can you push to a vector stored in a struct field? Can you write `v[0].x = 5` on a vector of structs?
  - Does `string` count as a collection?
  - A user-defined container can't opt into the shallow behavior the built-ins get.
  - **Worst case:** if a `bind` collection can be mutated, what does `&[int]` guarantee? If you can insert through a shared reference, you're back to modifying a collection while iterating over it, which is exactly what borrowing is supposed to prevent.
  - **Recommendation:** make `bind` deeply immutable everywhere.
- **`let` meaning mutable** will surprise people coming from Rust, Swift, or JS, where `let` means immutable or neutral. It's a valid choice, but expect confusion.
- **Shadowing**: is it allowed?
- **Annotation syntax is inconsistent:**
  - `count?: int` uses a colon.
  - Parameters `(a int)` don't.
  - Fields `x: int` do.

### §3.3 / §10 Functions
- **Return types:** there is no syntax to declare one. Recursion and mutual recursion need either an annotation or inference across the whole cycle of functions.
- **Function types:** the syntax is never given. The interface section implies `() string`.
- **Closures:**
  - Can a lambda capture variables from its scope? If `(a int) a * b` captures `b`, a plain C function pointer won't work.
  - Are captures moved or borrowed?
  - Is a local `bind f = ...` lifted out to a top-level C function?
- **Parsing:** `(a int) a + b` vs. a parenthesized expression `(a) b`. This only works if parameters must always be typed, so state that. Also, `() expr` could be confused with an empty tuple.
- **Order:** do top-level declarations depend on order?
- **Mutable methods:** `let Point.length = ...` would allow monkey-patching. Forbid it?

### §4.1 Numerics
- **"Smallest fitting type"** contradicts `[1, 2, 3] // type: [int]` ([L192](../specification/v0.1_SPECIFICATION.md#L192)). Under the rule as written, `let x = 10` is an `i8`, and `x * 100` overflows. The likely intent is that literals are **untyped constants that take their type from context and default to `int`**.
- **Undefined behavior:** overflow, division by zero, and shifts need defined semantics. Signed overflow is undefined behavior in C, and you don't want to inherit that.
- **Size types:** there is no `usize`/`isize` for indices, lengths, and C interop.
- **Conversions:** there is no cast syntax. [L295](../specification/v0.1_SPECIFICATION.md#L295) passes ints to `sqrt`, which implies an implicit int-to-float conversion.
- **Copy semantics:** the copy list names `int, float, bool, char`. Do the fixed-width types copy? Plain-data structs like `Point`? Stack arrays? Is there an explicit `clone`?

### §4.2 Strings
- **Contradictory reference types:**
  - `&string` is described as a slice/view.
  - `&-string` is described as allowing `push` "without reallocating," but `push` *does* reallocate.
  - These need different representations. `&-string` must point to the owned string, while a slice is (pointer, length).
  - The same question applies to `&[int]`: does it point to a vector, or is it a slice? Can it view a `[3: int]` stack array? Consider a separate slice type.
- **Literals:** when does `"x"` allocate? Passing one to a `&string` parameter shouldn't.
- **Indexing and length:** are they in bytes or code points? `char` is 32-bit but storage is UTF-8.
- **`$ident` greediness:** what does it capture in `$user.name`, `$name's`, `$ready?`?
- **Two escapes:** `\$` and `$$` do the same thing. Pick one.
- **Infinite recursion in §9.1:** `int.to_string = "${self}"`. If interpolation calls `to_string`, this calls itself forever. You need a built-in formatting primitive underneath.

### §5 Ownership
- **Conditional moves:** if a value is moved in only one branch, the generated C needs runtime "drop flags" to know whether to free it.
- **Moving out of things:** what about moving out of a collection or a field (`let s = v[0]` where the elements are strings)? Partial moves out of a struct?
- **Loops:** does `for (item in my_list)` consume the list or borrow it? Do you write `for (x in &v)`?
- **Owned value to a `&T` parameter:** auto-borrow, or an error? The §11.3 example takes `&[int]` but never shows the call.
- **User-defined destructors:** missing. They are essential for file handles and sockets.
- **"Heap structs"** ([L118](../specification/v0.1_SPECIFICATION.md#L118)): never defined, and there is no way to put a struct on the heap (no `Box` equivalent). Recursive types like `next: ?Node` need one.

### §7 Collections
- **Stack-array literals:**
  - Is `[3: 7]` three 7s, or an error because only one element was given?
  - What about `[3: 1, 2]`?
  - When every element is listed, the count is redundant.
- **The colon means three things:** stack-array length, map key, and struct field. `[3: 1]` and `#[3: 1]` differ by one character but mean completely different things.
- **Empty literals:** `[]` and `#[]` (set or map?) need a type from context.
- **The `X[...]` ambiguity:** `Point[x: 1]` (construction), `pt[x]` (indexing), and `Circle[r]` (pattern) look alike. The parser has to know whether an identifier names a type, which is C's typedef problem. A capitalization rule would solve it, but `int` and other lowercase type names break that.
- **Out-of-bounds vector index:** panic, or `?T` like maps? Right now vectors and maps behave differently.
- **Map assignment:**
  - `ages["Diana"] = 28` assigns to an expression whose value is `?int`. You need rules for what can appear on the left of `=`.
  - `ages["x"] += 1`?
- **Map keys:** they need hashing and equality. Through an interface?
- **Stack arrays in C:**
  - C can't pass or return arrays by value, so they need to be wrapped in a struct.
  - Large arrays risk overflowing the stack.
- **Trailing-comma rule:** does it apply to parameters, call arguments, and match arms? How is "multiline" detected?

### §8 `define`
- **`define UserID int`:** a transparent alias, or a distinct new type? If it's an alias, then `UserID.to_string` defines `int.to_string`.
- **Grammar:** `define X <Kind> [...]` vs. `define X <Type>` requires the kind words to be reserved.
- **Name collision:** enum variant `Point` ([L263](../specification/v0.1_SPECIFICATION.md#L263)) collides with struct `Point` from §8.1. What does `when Point:` refer to? How is a variant constructed: `Shape.Circle[...]` or `Circle[...]`?
- **Positional destructuring:** `Circle[r]` binds by position although the fields have names. Reordering the fields silently breaks every match. Allow `Circle[radius: r]`?
- **Recursive types:** depend on the heap-allocation question from §5.

### §8.3 Interfaces
- **Receiver kind:** method signatures leave out how `self` is taken (`&self`, `&-self`, or owned). Both the vtable and the borrow checker need it.
- **Coherence:** interfaces are satisfied automatically, and methods can be added to any type from anywhere. So:
  - Two libraries can both define `int.to_string`, and they conflict.
  - Types can satisfy an interface by accident.
  - You'll need module-scoped methods or an orphan rule (only the module that owns the type or the interface may add the method).
- **Vtables:** "vtables for all implementing types" means every type × every interface. Generate them only where a value is actually converted to the interface.
- **Built-in methods:** can a user define `string.push` and shadow the built-in?

### §9 Methods
- Auto-borrowing at method calls vs. the mandatory `&-` (see A).
- Static functions and constructors with no `self`, like `Point.new`?
- Must the first parameter be named `self`? Can any function be called with dot syntax?

### §11 Control Flow
- **`in`:** if `x in set` is ever allowed as a boolean expression, `for (x in list)` becomes ambiguous with the while-style `for (cond)`.
- **Ranges:** is `0..10` exclusive? What is the inclusive syntax? Steps? Reverse ranges?
- **Dangling else** for nested braceless `if`s.
- **`if` without `else`** in a position that needs a value: an error?
- **`for (k, v in map)`:** is iteration order deterministic? Can vectors use `for (i, x in v)` to get indices?
- **Break values:** the types of different `for <- x` values must be unified.

### §13 C Transpilation
- **Blocks as expressions:**
  - Standard C has no statement-expressions; `({...})` is a GCC extension.
  - You need a lowering pass that rewrites nested expressions into temporaries, statements, and `goto`s.
  - Plan for it as a core pass, not an afterthought.
- **Evaluation order:** C leaves the order of function arguments unspecified. Lowlight needs to define one (left to right) and emit explicit sequencing.
- **Cleanup:**
  - Drop order: reverse declaration order?
  - Freeing temporaries.
  - Drop flags for conditional moves.
  - A `<-` in the middle of an expression.
- **Panics:**
  - What happens on an out-of-bounds index, out-of-memory, or overflow? Abort?
  - Does cleanup run on the way out?
- **Name mangling:**
  - `user?` isn't a valid C identifier.
  - `Point.length` isn't either.
  - User names can collide with C keywords or libc symbols.
- **Built-in generic collections:** generate a specialized copy per element type, or use `void*`?
- **Optional layout:**
  - An optional reference can be a nullable pointer.
  - That helps with calling C code, and it saves space.

---

## 3. Decisions to Make First
1. **Lifetimes:** Rust-style annotations, second-class references, or elision only?
2. **Optionals:** is `?T` or the `name?` suffix the primary system, and what does `let b = user?` mean?
3. **`match`:** what terminates it?
4. **`bind`:** deep or shallow immutability, consistently?
5. **Literals:** do they take their type from context (default `int`), or "smallest fitting"?
6. **Closures:** can they capture, and how does that work in C?
7. **`<-` and `&-`:** what is the lexing rule?

> [!TIP]
> Some of this is worth keeping as-is:
> - Required parentheses around conditions remove a lot of ambiguity about braceless bodies.
> - The lexically targeted `<-` neatly unifies break, continue, and return.
> - A loop with `else` that produces a value is elegant.
> - The mandatory call-site `&-` is a good transparency rule (once methods are reconciled with it).
