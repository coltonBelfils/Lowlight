## Part 1: Structural Questions & Follow-Ups

### A. Lifetimes: Option 1 vs. Option 2 (Pending Your Review)

Since you are leaning toward Option 2, here is the concrete breakdown of what you gain and what you give up with each, plus a middle option (**Option 2.5**) that removes Option 2's biggest pain point without adding lifetime syntax.

#### Option 1: First-Class References with Lifetime Annotations (Rust style)
References (`&T`, `&-T`) can be passed as arguments, returned from functions, and stored inside structs and collections. Because a struct or return value can hold a reference, the compiler needs lifetime parameters (`'a`) whenever there is more than one possible source for a borrow:
```
bind longest = (a &'a string, b &'a string): &'a string {
    if (a.len > b.len) a else b
}

define Token['a] struct [
    text: &'a string,
    line: int,
]
```
* **Pros:**
  * Zero-copy data structures: a struct like `Token` can hold a `&string` view directly into an input buffer without copying or allocating.
  * Functions can return references into collections (`map.get(k)` returning `?&V`) or pick between multiple borrowed inputs.
* **Cons:**
  * **Viral annotations:** Putting `&T` inside a struct requires annotating the struct, every struct that contains it, and functions using it.
  * **High complexity:** Requires a full region/lifetime solver in the compiler and makes the language feel much heavier.

#### Option 2: Strict Second-Class References (Hylo / Val style)
`&T` and `&-T` are **scoped borrows**, not storable types:
1. Function parameters can be `&T` or `&-T`.
2. Local variables can be `&T` or `&-T`, and their borrow ends at the end of their block (or after their last use).
3. **Structs, enums, and collections cannot contain `&T` or `&-T` fields/elements.**
4. **Functions cannot return `&T` or `&-T`.**

* **Pros:**
  * **Zero lifetime annotations** anywhere in the language.
  * **Simple mental model & compiler:** At any function call `foo(&a, &-b)`, the compiler only checks that the arguments don't conflict with each other. As soon as `foo()` returns, all borrows passed into it are done.
  * **Impossible to create dangling references** by construction.
* **Cons (the two pain points of pure Option 2):**
  1. **Inspecting non-copy elements in collections:** If `users["alice"]` returns `?User` by value, and `User` owns heap strings, looking up a user in a map either has to **copy/clone** the `User` or **move** it out of the map. You cannot write a helper that returns `&User` from inside a collection.
  2. **No reference-holding structs:** A parser `Token` struct cannot hold `&string`; instead, you store integer offsets `(start: int, end: int)` into the source string (which is common in C/Zig because integer indices don't break when a buffer reallocates).

#### Option 2.5: Second-Class References + Tied Return Borrows (Recommended if you want Option 2)
Keep the rule that **structs and collections can never store `&T` or `&-T`**, so there are still zero lifetime annotations on types. However, allow a function or method to return `&T` or `&-T` **under one strict rule**:
* A function returning a reference must borrow it from `self` (if it's a method) or from its **sole borrowed parameter** (if it's a free function).
* Example:
  ```
  // Legal: only one borrowed input (`self`), so the returned `&User` obviously borrows `self`
  bind Team.leader = (self &Team): &User {
      &self.members[0]
  }
  ```
* While the returned `&User` is still in use by the caller, the caller's `team` remains borrowed.
* This gives you 90% of Option 1's ergonomics (returning slices, views, and references into containers) with **zero lifetime syntax** and Option 2's simplicity.

### B. Call-Site `&-`, Method Auto-Borrowing, and Reborrowing (Pending Your Review on Reborrowing)

* **Method Auto-Borrowing vs. Explicit Call-Site `&-` (Resolved):**
  * Method syntax `pt.translate(5, 5)` implicitly borrows the receiver (`pt`) according to the method's `self` parameter (`&Point` or `&-Point`), checking that `pt` was declared with `let` if `self` is `&-`.
  * Direct call syntax `Point.translate(&-pt, 5, 5)` and all non-receiver arguments `push(&-my_list, 4)` **must** write `&-` explicitly.

* **How Reborrowing Should Work (My Recommendation):**
  Suppose a function already has a mutable borrow `list &-[int]` and passes it to another function:
  ```
  bind push_two = (list &-[int], a int, b int) {
      push(&-list, a)
      push(&-list, b)
  }
  ```
  If `&-` always added another pointer level, `&-list` would have type `&-&-[int]`, which wouldn't match `push`'s parameter type `&-[int]`. And if you wrote `push(list, a)` without `&-`, it would break your call-site transparency rule and move `list` on the first call.
  * **Recommended Rule — Reference Flattening (Reborrowing):**
    1. Nested reference types (`&&T`, `&-&-T`, `& &-T`) do not exist.
    2. Writing `&-x` when `x` is already a `&-T` **reborrows** `x` as `&-T` for the duration of that call (temporarily lending exclusive access to the callee, then restoring it when the call finishes). In C, it simply passes the pointer value through.
    3. Writing `&x` when `x` is `&T` or `&-T` reborrows `x` as a read-only `&T`.
    4. Writing `&-x` when `x` is an immutable `&T` is a compile error.

### C. Go-Style Semicolon / Newline Rules Adapted for Lowlight (Pending Your Review)

Translating Go's rule into Lowlight works very well, with two small adjustments for Lowlight's `[]`/`()` delimiters and expression-oriented `if`/`match`:

1. **Inside `(...)` and `[...]`:** Newlines are ignored as statement separators (they act as normal whitespace, while still triggering the multiline trailing-comma check in §7.3).
2. **Inside `{...}` and at top level:** A newline acts as a `;` **if and only if** the last token before the newline is:
   * An **identifier** (`x`, `foo`, `user?`)
   * A **literal** (`42`, `3.14`, `"hi"`, `'a'`, `true`, `false`, `none`)
   * A **closing delimiter**: `)`, `]`, or `}`
   * A **built-in type name** (`int`, `u8`, `string`, etc. — so `define UserID int` ends at the newline)
   * A **bare unwind** `<-` (when used without a value)
3. **Next-Line Continuation Exceptions (where Lowlight differs from Go):**
   Even if Rule 2 would insert a `;`, the `;` is **not** inserted if the first token on the next line is:
   * `else` (so `if (c) 1` followed by `else 2` on the next line stays one `if` expression)
   * `when` (so multiline `match` arms stay attached to `match`)
   * `.` (optional, but recommended so fluent method chains like `items\n .filter(...)\n .map(...)` work across lines)

* **Consequence for binary operators:** Just like in Go, splitting a math or boolean expression across lines requires putting the operator at the **end** of the line (`let x = a +\n b`), because `let x = a\n - b` parses as `let x = a; -b`.

### D. Terminating `match`: `end` vs. Indentation vs. Better Fits (Pending Your Review)

Between `end` and significant indentation:
* **`end`** is much safer than indentation. Making *only* `match` indentation-sensitive in a language that otherwise uses `{}` and `[]` causes subtle bugs when code is reformatted, copy-pasted, or placed inside function arguments.
* However, you are right that `end` feels out of place when nothing else in Lowlight uses `end`.

Here are **three alternatives** that fit Lowlight's existing rules without `end` or indentation:

1. **Option 1: Wrap `match` in `{ ... }` (Fits Principle 4!)**
   ```
   let area = match (my_shape) {
       when Circle[r]: 3.14159 * r * r
       when Rectangle[w, h]: w * h
       when Point: 0.0
   }
   ```
   * *Why it doesn't violate Principle 4:* Principle 4 says `{}` is for **executable block expressions**, while `[]` is for data and type definitions. A `match` is an executable control-flow expression that evaluates to a value. Using `{}` makes `match` consistent with `if` and `for`, makes nested `match` unambiguous, and lets exhaustive enum matches omit `else`.

2. **Option 2: Wrap `match` in `[ ... ]` with commas (Treat `match` as a Pattern Map)**
   ```
   let area = match (my_shape) [
       when Circle[r]: 3.14159 * r * r,
       when Rectangle[w, h]: w * h,
       when Point: 0.0,
   ]
   ```
   * *Why it fits:* It mirrors `#[Key: Value]` and `define Shape enum [...]` and uses your §7.3 trailing-comma rule.

3. **Option 3: Greedy `when`/`else` Continuation + `(...)` for Nested Matches**
   Keep your current bracket-free syntax! Under the Go-style newline rule above, `match (expr)` simply keeps consuming `when` arms (and an optional final `else` arm) as long as the next token is `when` or `else`. As soon as the next statement starts with anything else, the `match` ends.
   * To prevent ambiguity when nesting a `match` inside another `match`, the compiler simply requires an inner `match` arm to be wrapped in `(...)` or `{...}`:
     ```
     let res = match (a)
         when 1: (match (b)
             when true: "x"
             else: "y")
         else: "z"
     ```
   * This preserves your exact current syntax while solving both exhaustive enum matches (no `else` needed) and nested matches.

### E. Optionals: Resolved Rules & Follow-Up on `if (user?)` Borrow Syntax

#### Resolved in Round 1 & Round 2:
* Underlying type is `?T`, and any variable holding `?T` must have a `?` suffix (`user?`).
* `user` (`T`) and `user?` (`?T`) are separate identifiers; inside `if (user?)`, `user` shadows any outer `user`.
* `?(?T)` automatically flattens to `?T`, and `?T` is allowed inside collections.
* `if (flag?)` on `?bool` tests presence (`has_value`), not the boolean value.
* Return types are required on value-producing functions: `(): string` or `(): ?string`.
* Dot-chaining `.` works on both non-optionals and optionals (short-circuiting to `none` when the left side is `none`).
* In string interpolation, bare `$ident` only parses non-optional identifiers (without `?`), so `"Are you $ready?"` treats `?` as literal punctuation.

#### Follow-Up Question: Should `if (user?)` Have Syntax Showing It Is a Borrow?
You asked: *"Then yes treat it as a borrow. Should there be syntax to show it is a borrow?"*

Compare these two ways to handle `if` unwrapping:

1. **Option 1: Implicit Immutable Borrow `if (user?)`, Explicit Mutable Borrow `if (&-user?)` (Recommended)**
   * Just like method calls (`user.length()`) implicitly borrow `&user` without requiring `&`, writing `if (user?)` implicitly binds `user` as a read-only borrow (`&User`) of `user?` for the duration of the `if` block (or copies it for primitives like `int`).
   * If you want to **mutate** the inner value inside `user?` during the `if` block, you must write `if (&-user?)`:
     ```
     // Read-only borrow (95% of cases — clean and concise):
     if (user?) {
         print(user.name)
     }

     // Mutable borrow into `user?` (explicit `&-`, matching your call-site rule!):
     if (&-user?) {
         user.name = "Updated" // mutates the User inside `user?`!
     }
     ```
   * **Why this fits Lowlight:** You don't clutter everyday read-only `if (user?)` checks with `&`, while still enforcing your core rule that **in-place mutation always requires an explicit `&-`**.

2. **Option 2: Always Explicit (`if (&user?)` vs. `if (&-user?)` vs. `if (user?)`)**
   * `if (&user?)` borrows `user` immutably (`&T`).
   * `if (&-user?)` borrows `user` mutably (`&-T`).
   * `if (user?)` **moves** (or copies, for primitives) the value out of `user?`, consuming `user?`.
   * *Tradeoff:* Allows moving an owned value out of an optional inside an `if`, at the cost of having to write `&` on every read-only `if (&user?)` for heap types. (Note: you can already move out of an optional using `let user = user? ?? ...`, so Option 1 is usually much nicer in practice.)

### F. Unwinding (`<-`) & Rethinking `for` Loops Around Expressions

#### Resolved in Round 1 & Round 2:
* `<-` only unwinds `{ ... }` blocks or named targets (`if <-`, `for <-`, `func <-`, `label <-`).
* Unwinds cannot cross a function or lambda boundary (compile-time error).
* Void functions (omitting `:ReturnType`) and void loops are supported.

#### Follow-Up 1: Rethinking `for` Loops (Both the Loop and Each Iteration as Expressions)
You wrote:
> *"The `for` loop itself is an expression, but so is each iteration—each one uses block expressions or a single non-block expression. `for` loops should be made with that consideration in mind. I think that'll mean `for` loops look and behave considerably different than a traditional loop. I want the expression nature of both the loop itself and the expression nature of each iteration to be accounted for."*

This is a really exciting direction. In traditional languages, the body of a `for` loop throws away its value at the end of every iteration. If instead **each iteration's body is an expression that produces an iteration value**, and **the `for` loop as a whole is an expression that combines those iteration values**, `for` becomes much more powerful and unified!

Here are **three ways** to design that relationship between the *iteration expression* and the *overall loop expression*:

##### Design 1: Iteration Values Collect into a Vector (`[T]`) by Default
If each iteration of a `for` loop evaluates to a value of type `T`, what is the most natural value of the whole loop? **A vector `[T]` of all the values produced by each iteration!**
```
// 1. Single expression body: each iteration yields `x * 2`, so the loop yields `[int]`!
let doubled = for (x in numbers) x * 2

// 2. Block expression body: each iteration's `{ ... }` evaluates to its last expression:
let labels = for (x in numbers) {
    let squared = x * x
    "Value: $squared" // <- iteration evaluates to `string`, so `labels` is `[string]`!
}
```
Now look at how your unwind operator `<-` controls **both** levels cleanly:
* **`<- val` (or `next <- val`)**: Ends the **current iteration's `{}` block** early, yielding `val` as this iteration's element in the result vector!
* **`next <-` (bare, no value)**: Skips the **current iteration** without adding an element to the result vector! (Wait—that means `for` + `if (skip) next <-` does **map and filter** in one construct!)
  ```
  // Collects only positive numbers, doubled (`[int]`):
  let pos_doubled = for (x in numbers) {
      if (x <= 0) next <-
      x * 2
  }
  ```
* **`for <- val`**: Aborts the **entire loop** immediately and makes the whole `for` expression evaluate to `val` (the search / early-exit loop you already have in the spec!).
* **Void body (no final expression in `{}`)**: If the body block ends in a statement (like `print(x)` or an assignment) instead of a value expression, the iteration produces no value and the loop is simply a side-effect loop.

##### Design 2: Iteration Value Feeds the Next Iteration (Accumulator / Fold Model)
What if instead of building a vector `[T]` on the heap, the loop carries a state value from one iteration to the next, and each iteration's expression evaluates to the **next iteration's state**?
```
// `sum` starts at 0.
// Each iteration's block evaluates to the new value of `sum`!
// When the loop finishes, the whole `for` expression evaluates to the final `sum`!
let total = for (x in numbers, sum = 0) {
    if (x < 0) <- sum  // exits this iteration's block early, keeping `sum` unchanged!
    sum + x            // evaluates to the new `sum` for the next iteration!
}
```
* **Why this is cool for a low-level language:**
  * Zero hidden heap allocation (unlike collecting into `[T]`).
  * Inside the loop body `{ ... }`, `<- val` literally just means *"evaluate the current iteration's block to `val`"*, which automatically acts as `continue` with the state `val`!
  * `for <- val` still breaks out of the entire loop early with `val`.
  * You don't even need to mutate outer variables with `let`—a `for` loop is a pure expression that transforms an initial value across iterations!

##### Design 3: Supporting Both via Syntax (or Explicit Target)
You can actually support **all three** loop expressions under one consistent rule by looking at the loop header and body:
1. **Stateful / Fold Loop (`for (x in list, acc = init) { ... }`)**: Each iteration's block must evaluate to the type of `acc`, updating `acc` for the next step. The whole `for` evaluates to the final `acc` (type `T`).
2. **Search / Early-Exit Loop (`for (x in list) { if (...) for <- x } else { default }`)**: Body doesn't evaluate to a per-iteration value, but uses `for <- val` to break out with a result (type `T` with `else`, or `?T` without `else`).
3. **Comprehension / Collecting Loop (if desired)**: Could either be the default when a stateless `for (x in list)` has a value-returning body (`let squares = for (x in list) x * x`), or use `#[...]` / `[for (x in list) x * x]`.

Which of these (`Design 1: Collect to [T]`, `Design 2: Fold/Accumulator per iteration`, or `Design 3: Combined`) matches how you picture each iteration being an expression?

#### Follow-Up 2: Where Can `<-` Unwind Statements Appear?
You asked:
> *"Or would it be better to not let unwind statements in expressions, but just in assignment statements or as bare unwind statements?"*

**Yes—restricting `<-` to statement positions and top-level `??` in assignments/declarations is much cleaner!**

Specifically, if the rule is:
1. **Standalone unwind statement:** `target <- val` (or bare `target <-`) as its own statement in a block, or as the body of an `if` / `match` arm:
   ```
   if (n == 999) func <- none
   ```
2. **Right-hand side of a top-level `??` in a `let` / `bind` / assignment:**
   ```
   bind user = find_user(id) ?? func <- none
   ```
3. **Forbidden inside nested sub-expressions or function call arguments:**
   ```
   // COMPILE ERROR: cannot put `<-` inside function call arguments or math expressions
   print_two_strings(make_header(), user?.name ?? func <- -1)

   // Instead, write it clearly in two steps:
   bind name = user?.name ?? func <- -1
   print_two_strings(make_header(), name)
   ```

* **Why this is the better rule:**
  * Keeps your distinction between **statements** (`let`, `bind`, `=`, `<-`) and **expressions** sharp and consistent.
  * Completely prevents the mid-expression temporary memory leak hazard without needing complex C expression-hoisting for unwinds.
  * Makes control flow obvious—a function call's arguments can never secretly return from the caller before the function is even called.

## Part 2: Section-by-Section Critique (Ready for Your Comments)

### §1 Principles
* **"Zero hidden runtime overhead" vs. Heap Defaults:**
  * `let s = "Hello"` allocates a heap `string` ([L96](../../SPECIFICATION.md#L96)).
  * String interpolation `"Hello, $name!"` allocates on the heap.
  * This isn't bad design—it's ergonomic—but Principle 1 may want to say *"predictable, deterministic memory management"* rather than *"zero hidden runtime overhead"*, or string literals should default to `&string` (static read-only slice) unless converted to an owned `string`.
* **"Explicit pointers" & C Interop:** The spec mentions explicit pointers in Principle 1, but there is no raw pointer type or `extern` C function syntax yet.
* **Principle 3 & 4 Wording:**
  * Update Principle 3 to reflect your clarification that declarations, assignments, and `<-` unwinds are statements, and functions can be `void` (non-value-returning).
  * Update Principle 4 to note that `[]` is also used for indexing (`ages["Diana"]`), destructuring patterns (`Circle[r]`), and possibly `match` (if you pick `[...]` for `match`).

### §2 Lexical
* Still to specify when you're ready:
  * Multi-line comments (`/* ... */`?).
  * Escape sequences in strings/chars (`\n`, `\t`, `\"`, `\\`).
  * Character literal syntax (`'a'`) vs. string literals (`"a"`).
  * Numeric literal formats: hex (`0xFF`), binary (`0b1010`), underscores (`1_000_000`).

### §3 `let` / `bind`
* **Deep vs. Shallow Immutability for `bind` Collections ([§3.2](../../SPECIFICATION.md#L62-L68)):**
  * Right now, `bind pt = Point[x: 1, y: 2]` is **deeply immutable** (cannot mutate `pt.x` or call `pt.translate(5, 5)` because `translate` takes `&-Point`).
  * Yet `bind cache = #["a": 1]` is **shallowly immutable** (`cache.insert("b", 2)` is allowed, even though `insert` mutates the map and requires `&-`!).
  * This creates three problems:
    1. If a `Point` contains a vector field `items: [int]`, is `bind p = ...; p.items.push(1)` allowed or forbidden?
    2. What about `string`—is `bind s = "hi"; s.push("!")` allowed like a vector, or forbidden like a primitive?
    3. Most importantly: if `bind` allows mutating a collection, why have `let` vs `bind` at all for collections, and how does the compiler know a `bind` collection won't be mutated while borrowed as `&[int]`?
  * **Suggestion:** Make `bind` **deeply immutable for everything** (including Vectors, Maps, Sets, and Strings). If you want to insert into a map or push to a vector, you declare it with `let cache = #["a": 1]`. That makes `let` = mutable and `bind` = immutable with zero exceptions!
* **Type Annotation Colon Consistency:**
  * Struct fields use a colon: `x: int`
  * Function return types use a colon: `(a int, b int): int`
  * Explicit local variable types use a colon: `let count?: int = none` ([L150](../../SPECIFICATION.md#L150))
  * Function parameters do **not** use a colon: `(a int, b int)`
  * Is omitting the colon in parameters intentional, or would you rather have `(a: int, b: int)` everywhere?
* **Variable Shadowing:** Since `if (user?)` shadows an outer `user`, can regular `let` or `bind` declarations in an inner block (or the same block) also shadow an existing variable?

### §3.3 / §10 Functions & Closures
* **Function Type Syntax:** With return types written `:Type`, how do you write the type of a function variable or callback parameter? E.g., `(int, int): int` and `(): string`?
* **Can Anonymous Functions (Lambdas) Capture Variables?**
  * In [§3.3](../../SPECIFICATION.md#L73-L75):
    ```
    let current_op = static_add
    current_op = (a int, b int): int a * b
    ```
  * If `(a int, b int): int a * b` does **not** capture any local variables from its surrounding scope, it compiles directly to a plain C function pointer (`int64_t (*current_op)(int64_t, int64_t)`).
  * If it **does** capture a local variable (`let factor = 3; current_op = (a int, b int): int (a + b) * factor`), C has no native closures—so a plain C function pointer cannot hold `factor`! You have two choices:
    1. **No capturing lambdas (C / Zig style):** Anonymous functions cannot capture local variables, so every function value is a plain C function pointer.
    2. **Fat-pointer closures:** Function values are `{ fn_ptr, env_ptr }`, or capturing is only allowed for borrowed callback parameters.
* **Forbid `let Type.method`:** In §9, methods are declared with `bind Point.length = ...`. You probably want to forbid `let Point.length = ...` so methods on a type cannot be reassigned at runtime.

### §4.1 Numerics
* **"Smallest Fitting Type" vs. `[1, 2, 3] // type: [int]`:**
  * [§4.1](../../SPECIFICATION.md#L84) says: *"Numeric literals automatically infer the smallest fitting type when inferring types."*
  * Under that wording, `let x = 10` would infer `i8` (or `u8`), and `x * 20` would immediately overflow! It also contradicts `[1, 2, 3]` being `[int]` in [§7.1](../../SPECIFICATION.md#L192).
  * **Likely intent:** Numeric literals adapt to a known target type if they fit (`let b: u8 = 10` or `take_u16(500)` works without a cast), and **default to `int` (`i64`) / `float` (`f64`)** when no target type is specified (`let x = 10` is `int`).
* **Type Conversions / Casting:** How do you convert `int` to `float` or `u8` to `int`? In [§9](../../SPECIFICATION.md#L295), `sqrt(self.x * self.x + self.y * self.y)` passes an `int` into `sqrt`. Are numeric conversions explicit (e.g., `float(x)` or `x as float`)?
* **Copy vs. Move Types:**
  * [§5.1](../../SPECIFICATION.md#L117) says scalar primitives (`int`, `float`, `bool`, `char`) are copied rather than moved.
  * What about a stack struct or enum that only contains primitives, like `Point[x: int, y: int]` or `[3: int]`? In C, small structs are copied by value; in Rust, types must opt into `Copy`. Should structs/arrays made purely of copyable fields also be copied by value, or moved?

### §4.2 Strings
* **`&string` vs. `&-string` Representation:**
  * `&string` is a read-only view/slice (`{ const char* data; int64_t len; }`), which can point into a static C string literal `"hello"` or a substring without allocating.
  * `&-string` allows `.push(" [TAG]")`, which can **reallocate** the underlying heap buffer and change `capacity`. So `&-string` must be a pointer to the owned `string` struct (`String*`), whereas `&string` is a view (`StringView`).
  * Note: Change the wording on [L101](../../SPECIFICATION.md#L101) from *"allowing in-place modification without reallocating"* to *"allowing in-place mutation of the caller's string without moving ownership"* (since `.push()` may reallocate the heap buffer when capacity is exceeded).
* **Duplicate Dollar Escape:** [L110](../../SPECIFICATION.md#L110) lists both `\$` and `$$` to escape `$`. Pick one (`\$` is standard alongside `\n` and `\"`).
* **Infinite Recursion in [§9.1](../../SPECIFICATION.md#L312-L314):**
  ```
  bind int.to_string = (self &int): string {
      "${self}"
  }
  ```
  If `"${self}"` works by calling `self.to_string()`, then `int.to_string` calls itself infinitely! Built-in primitives should either have `to_string` built in, or `"${...}"` on primitives should call the C runtime formatter directly.

### §5 Ownership & Borrowing
* **Iterating in a `for` Loop — Move or Borrow?**
  * In `for (item in my_list) { ... }`, does the loop **borrow** `my_list` (so `my_list` can still be used after the loop), or **consume/move** `my_list`?
  * For a collection of heap strings (`my_list: [string]`), what is the type of `item`—a borrowed `&string` or a moved `string`? (Borrowing elements as `&T` by default in `for (item in my_list)` so the list isn't destroyed by looping over it is usually much nicer!)
* **Recursive Structs / Heap Allocation:**
  * How do you define a recursive struct like a tree node or linked list (`define Node struct [ val: int, next?: ?Node ]`)? In C, a struct cannot contain itself by value (infinite size); it needs a heap pointer. Does Lowlight have a way to heap-allocate a single struct, or are recursive structures built using vectors/arenas?

### §7 Compound Data Structures
* **Stack Array Syntax `[N: ...]` ([§7.1](../../SPECIFICATION.md#L195-L200)):**
  ```
  let s = [3: 1, 2, 3]  // 3 elements listed: 1, 2, 3
  let buffer = [100: 0] // 1 element listed, repeated 100 times
  ```
  * Look at the ambiguity when `N` is `1` or when someone makes a typo:
    * `[1: 5]` — is that a 1-element stack array `[5]`, or a map typo for `#[1: 5]`?
    * `[3: 5]` — is that three `5`s (`[5, 5, 5]`), or a compile error because the programmer wrote `3:` but only supplied 1 element?
    * Why require `3:` in `[3: 1, 2, 3]` when the compiler can count that there are 3 elements?
  * **Cleaner idea:** What if `[3: 0]` **always** means *"repeat `0` three times on the stack"*, and listing explicit elements on the stack uses a slightly different marker (or type annotation `let s: [3: int] = [1, 2, 3]`)?
* **Vector Out-of-Bounds Indexing:**
  * Map lookup `ages["Alice"]` returns an optional `?int`.
  * What does vector/array indexing `v[i]` return? Does `v[i]` return `T` (and panic/abort at runtime if `i` is out of bounds, plus allow `v[i] = 10`), or does it return `?T`?
* **Empty Collection Literals:**
  * An empty vector `[]` doesn't reveal its element type, and `#[]` doesn't reveal whether it's an empty Set or an empty Map.
  * Require an explicit type on the variable when initializing empty collections (`let v: [int] = []`, `let m: #[string: int] = #[]`)?

### §8 `define` (Structs, Enums, Interfaces, Type Aliases)
* **Enum Variant Naming Collision ([§8.2](../../SPECIFICATION.md#L260-L264)):**
  * §8.1 defines `define Point struct [ x: int, y: int ]`.
  * §8.2 defines `define Shape enum [ Circle [...], Rectangle [...], Point ]`.
  * Both are named `Point`! And in §12, `when Point: 0.0` matches the enum variant without `Shape.`.
  * Should enum variants always be qualified with their enum name (`Shape.Circle[radius: 5.0]`, `Shape.Point`, `when Shape.Point:`)? Qualifying them (or requiring `.Circle` shorthand when the enum type is known) prevents enum variants from colliding with struct names!
* **Enum Destructuring — Positional vs. Named ([§8.2](../../SPECIFICATION.md#L261) vs. [§12](../../SPECIFICATION.md#L433)):**
  * `Circle` is defined with a named field: `Circle [ radius: float, ]`.
  * How do you construct a `Circle`? `Shape.Circle[radius: 5.0]`?
  * In `match`, it is destructured by position: `when Circle[r]:`. What if a struct or enum has fields reordered later? Allowing `when Circle[radius: r]:` (or shorthand `when Circle[radius]:` which binds a variable named `radius`) is much safer than positional matching on named fields.
* **Interface Method Receivers ([§8.3](../../SPECIFICATION.md#L269-L271)):**
  ```
  define Printable interface [
      to_string: () string,
  ]
  ```
  * Does `to_string` borrow `self` immutably (`&self`) or mutably (`&-self`)?
  * If an interface method can mutate the object, then calling it on an interface requires a mutable interface reference `&-Printable`. So the interface signature should indicate whether `self` is `&` or `&-` (e.g., `to_string: (&self): string`, or default to `&self` unless `&-self` is written).
* **`define UserID int` — Alias or Distinct Type? ([§8.4](../../SPECIFICATION.md#L282)):**
  * Can you pass a regular `int` to a function expecting `UserID` without converting it?
  * If you write `bind UserID.to_string = ...`, does that define a method only on `UserID`, or on all `int`s?

### §11 Control Flow & Operators
* **Lexing `<-` and `&-` Without Ambiguity:**
  * In `if (x<-5)`, does the lexer see `x` `<-` `5` (unwind to label `x` with `5`) or `x` `<` `-5` (is `x` less than `-5`)?
  * Simple rule to prevent this: **`<-` requires whitespace around it** (or `-5` after `<` requires whitespace/parentheses), and `&-` is only valid as a prefix unary operator (`&-expr` or `&-Type`), never as a binary operator.
* **Range Syntax (`0..10`):**
  * Is `0..10` exclusive (`0` through `9`)?
  * Is there an inclusive range (`0..=10` or `0...10`)?
* **`for (k, v in my_map)` vs. Vectors:**
  * Since maps support two loop variables `for (k, v in my_map)`, can vectors also support `for (i, item in my_list)` where `i` is the index and `item` is the element?
