### D. Terminating `match`: Idea 1 (`else:` / `else Pattern:`) vs. Your Question on Idea 3

You noted that you are leaning toward **Idea 1** (*"I'm leaning toward this idea. It's the cleanest"*), and asked a great question about **Idea 3**:
> *"This is intriguing. How would `when 200 <- "OK"` know to compare 200 to status_code? If we go this route when would need to be a valid keyword in every block context."*

You just put your finger on the exact flaw with Idea 3! Let's trace what happens if you try to make `match (status_code) { when 200 <- "OK" ... }` a normal `{ ... }` block:
1. **In any normal `{ ... }` block, you *already* have conditional unwinds using `if`!**
   You can already write this in Lowlight today without `match` or `when`:
   ```
   let label = {
       if (status_code == 200) <- "OK"
       if (status_code == 404) <- "Not Found"
       "Unknown"
   }
   ```
2. **Why `when 200 <- "OK"` inside `{ ... }` breaks down:**
   * In a normal `{ ... }` block, there is no implicit value to compare `200` against—so `when 200` would have no idea what it's matching unless `match (status_code)` secretly injected a hidden "current topic" into the `{ ... }` block.
   * Worse: what if you put an `if` block *inside* that `match` block?
     ```
     let label = match (status_code) {
         when 200: {
             if (is_admin) <- "Admin OK" // Wait: `<-` unwinds the inner `{}` block, NOT the `match`!
             "User OK"
         }
         "Unknown"
     }
     ```
     Because `{ ... }` is a block, `<-` inside an inner `{ ... }` unwinds the *inner* block rather than the `match`!

#### Why Idea 1 (`match (x) when ... else ...`) Is So Clean
By keeping `match` container-free and requiring **every `match` to end with `else`** (`else: expr` for open/fallback matches, or `else FinalVariant: expr` for exhaustive enums):
* `{ ... }` stays 100% pure: a `{ ... }` block is *always* a sequence of statements/expressions, never a special pattern container.
* `match` never needs `{ ... }`, `[ ... ]`, `( ... )`, or `end`, because **the `else` arm is always the final arm of every `match`**:
  ```
  // 1. Open match with catch-all `else:`:
  let label = match (status_code)
      when 200: "OK"
      when 404: "Not Found"
      else: "Unknown"

  // 2. Exhaustive enum match (ends at `else FinalVariant:`, compiler still verifies exhaustiveness!):
  let code = match (status)
      when Status.Pending: 1
      when Status.Active: 2
      else Status.Closed: 3

  // 3. Multi-statement arm inside `match` (uses a real `{ ... }` block for that arm's value!):
  let msg = match (status_code)
      when 500: {
          log_error("Server crash")
          "Internal Error" // <- normal `{}` block returning a string!
      }
      else: "OK"
  ```

### F. Full Explanation & Multi-Context Showcase: Design 3 ("Last Iteration Wins") for `for` Loops

You asked:
> *"Let's go with this one. Give me a full explanation of it and show me it in a bunch of different contexts—traditional for loop, list iteration, map iteration, map/reduce if possible, …"*

And you also asked a crucial question on the earlier `first_even?` example:
> *"In this example, how would the compiler know what type `first_even?` is? ... The for loop's value can be ignored and then it looks like a traditional for loop, but if the loop is going to return a value, is it going to be `[T]` or `T`. It can't be both. It should only always be one."*

**Exactly!** That is the huge advantage of **Design 3**:
In Design 3, **a `for` loop NEVER returns an array `[T]`**. If a `for` loop returns a value, it **ALWAYS returns a single value (`T` or `?T`)**—just like an `if` expression or a `{ ... }` block!

---

#### 1. The Complete Rules of Design 3 ("Last Iteration Wins")

Think of a `for` loop as a `{ ... }` block that runs $N$ times in a row:

1. **What Each Iteration Evaluates To:**
   * The body of a `for` loop is either a single expression (`for (x in list) expr`) or a block (`for (x in list) { ... }`).
   * Inside the loop body, `next <- val` (or `<- val` at the top level of the loop's `{}` block) ends the **current iteration** early with `val` and starts the next iteration.
   * `for <- val` aborts the **entire `for` loop** immediately and makes the whole `for` expression evaluate to `val`.
2. **What the Whole `for` Loop Evaluates To:**
   * **If the loop body ends in a value expression of type `T`**:
     Each iteration produces a `T`. When the loop finishes running, the `for` expression evaluates to **the value produced by the last iteration that ran** (or `for <- val` if it broke early).
     * What if the loop ran **0 times** (e.g., `numbers` was empty `[]`)?
       * If there is an `else` clause (`for (...) { ... } else { fallback }`), the loop evaluates to `fallback` (so the loop's type is guaranteed **`T`**).
       * If there is **no `else` clause**, the loop evaluates to `none` (so the loop's type is **`?T`**).
   * **If the loop body ends in a statement (no bottom expression), but contains `for <- val` (a Search Loop)**:
     Normal iterations just advance to the next step without producing a value.
     * If `for <- val` is hit on some iteration, the loop immediately evaluates to `val`!
     * If the loop finishes all iterations without hitting `for <- val`, it evaluates to the `else` clause (type **`T`**) or `none` if there is no `else` (type **`?T`**).
   * **If the loop is used as a statement (not assigned to a variable or returned)**:
     It runs as a traditional `void` loop (any per-iteration value is ignored).

---

#### 2. Design 3 Across 8 Real-World Contexts

##### Context 1: Traditional Side-Effect / Counting Loop (`void` Statement Loop)
When you don't assign the `for` loop to a variable, it works 100% like a traditional loop:
```
// Exclusive range (0 through 9):
for (i in 0..10) {
    print("Step $i")
}

// Inclusive range (1 through 10) with `next <-` (continue) and `for <-` (break):
for (i in 1..=10) {
    if (i % 2 == 0) next <- // skips even numbers (bare `next <-` = continue)
    if (i > 7) for <-       // stops loop early (bare `for <-` = break)
    print("Odd: $i")
}
```

##### Context 2: List Iteration (Read-Only Borrow vs. In-Place Mutation)
Looping over a list borrows each element by default (`&T`), or borrows mutably with `&-` to modify elements in place:
```
// Read-only iteration (`u` is `&User`; `users` is NOT consumed and can be used after the loop!):
for (u in users) {
    print(u.name)
}

// In-place mutation (`score` is `&-int`; doubles every element inside `scores` with zero allocation!):
let scores = [10, 20, 30]
for (&-score in scores) {
    score = score * 2
}
// `scores` is now [20, 40, 60]
```

##### Context 3: Map Iteration (`for (k, v in my_map)`)
```
let inventory = #["apples": 5, "oranges": 0, "bananas": 12]

// Read-only map iteration (`k` is `&string`, `count` is `int`):
for (item, count in inventory) {
    if (count == 0) {
        print("$item is out of stock!")
    }
}

// Mutating map values in place (`&-count` is `&-int`):
for (item, &-count in inventory) {
    count = count + 10 // Restocks every item by +10!
}
```

##### Context 4: Search / Find Loop (How `first_even?` Knows Its Type!)
Look at how clean your `first_even?` example is under Design 3:
```
// 1. Without `else`: returns `?int` (`none` if no even number exists in `numbers`)
let first_even? = for (n in numbers) {
    if (n % 2 == 0) for <- n // `n` is `int`, so the compiler knows `for <- n` yields `int`, making the loop `?int`!
}

// 2. With `else`: returns guaranteed `int` (`-1` if no even number exists)
let first_even = for (n in numbers) {
    if (n % 2 == 0) for <- n
} else {
    -1
}
```
Why does the compiler know `first_even?` is `?int`? Because the only value exit from the loop is `for <- n` where `n` has type `int`, and since there is no `else` clause, an exhausted loop yields `none`—so the type is unambiguously `?int`!

##### Context 5: Reduce / Fold (Using "Last Iteration Wins"!)
Look at how "Last Iteration Wins" lets a `for` loop evaluate directly to a reduced value (like a sum, product, or running state):
```
// `running_sum` is updated each iteration, and the iteration block evaluates to `running_sum`.
// On the final iteration, `running_sum` holds the grand total, so `total` gets that final value!
let running_sum = 0
let total = for (x in numbers) {
    running_sum = running_sum + x
    running_sum // <- Each iteration evaluates to `int`; the last iteration's value becomes `total`!
} else {
    0 // If `numbers` was empty (0 iterations), `total` is 0!
}
```
And if you want to skip negative numbers during that reduce while still returning a value from every iteration:
```
let running_sum = 0
let pos_total = for (x in numbers) {
    if (x < 0) next <- running_sum // Ends this iteration early with current `running_sum`!
    running_sum = running_sum + x
    running_sum
} else {
    0
}
```
*(Or, if you don't even need the `for` loop itself to return the sum, you can just write `let sum = 0; for (x in numbers) { if (x < 0) next <-; sum = sum + x }` as a normal void loop!)*

##### Context 6: Iterative Approximation / Retry Loop (Where "Last Iteration Wins" Really Shines!)
Suppose you are polling a sensor, retrying a network request up to 3 times, or running Newton's method for 10 steps where you want to stop early if you hit the target, **or** just take the final step's value if all 10 steps run:
```
let guess = 1.0
let approx_sqrt = for (step in 1..=10) {
    guess = 0.5 * (guess + target / guess)
    if (abs(guess * guess - target) < 0.0001) {
        for <- guess // Converged early! Break out with `guess`
    }
    guess // Didn't converge early; after step 10, the loop evaluates to step 10's `guess`!
} else {
    0.0
}
```
In almost every other language, you have to declare an extra result variable outside the loop or duplicate the return logic after the loop. With "Last Iteration Wins", the loop body's final expression `guess` naturally provides the result after the 10th iteration!

##### Context 7: Mapping / Filtering into a New Vector
Because a `for` loop in Design 3 always evaluates to a single `T` (never `[T]`), building a new vector `[T]` in a loop is explicit and transparent:
```
let doubled_evens: [int] = []
for (x in numbers) {
    if (x % 2 == 0) {
        doubled_evens.push(x * 2)
    }
}
```
*(Note: If you also want a one-line shorthand for building a vector, you can always use a `.map(...)` / `.filter(...)` method with a lambda, like `numbers.map((x: int): int x * 2)`!)*

### 1. Variable Shadowing (§3.2): Understanding Option 1 vs. Option 2

You wrote:
> *"I want to lean toward option 1 but I want to better understand option 2 first"*

Here is the exact difference between **Option 1** and **Option 2**:

* **What BOTH Option 1 and Option 2 Allow (Same-Block Shadowing):**
  In both options, you can re-declare a variable with `let` or `bind` **in the same `{ ... }` block** to transform its value or lock it down from `let` to `bind`:
  ```
  bind process = (raw_input: &string): int {
      let x = parse_int(raw_input) ?? 0
      let x = x * 2          // ALLOWED in both Option 1 & Option 2 (same block)
      bind x = clamp(x, 0, 10) // ALLOWED in both Option 1 & Option 2 (freezes `x` as `bind`!)
      x
  }
  ```
  And in both options, `if (user?)` is allowed to shadow an outer `user`.

* **Where Option 1 and Option 2 Differ (Inner-Block Shadowing):**
  Suppose you have a variable `x` in an outer block, and you open a nested `{ ... }` block (like an `if` or a `for` loop) inside the same function:
  ```
  bind calculate = (items: &[int]): int {
      let total = 0
      for (item in items) {
          let total = total + item // <-- Nested `{}` block declares a NEW `total`!
      }
      total
  }
  ```
  * **Under Option 1 (Unrestricted Shadowing):**
    * The line `let total = total + item` inside the `for` loop is **legal**. It creates a brand-new variable named `total` that only exists until the end of that loop iteration, leaving the outer `total` at `0` forever.
    * *Why people like Option 1:* Maximum freedom—you can reuse short names like `i`, `x`, or `temp` inside nested blocks without caring if the outer function already used that name.
    * *Why people get bitten by Option 1:* If you meant to mutate the outer `total` (`total = total + item`) and accidentally typed `let total = total + item` out of habit, the code compiles without error and silently throws away your math.
  * **Under Option 2 (Same-Block Shadowing Only):**
    * Shadowing in the **same block** (`let x = 1; bind x = x + 2`) is **legal**, because the old `x` is dead and replaced for the rest of the function.
    * Shadowing in an **inner `{ ... }` block** (`let total = ...` inside `for`) is a **compile-time error**, because the outer `total` is still alive after the inner `}` closes!
    * *(Alternative Option 1.5: Allow Option 1 unrestricted shadowing, or only forbid shadowing a mutable `let` variable with another `let` inside an inner block.)*

Now that you see how Option 2 works, do you prefer **Option 1 (Unrestricted Shadowing)** or **Option 2 (Same-Block Shadowing Only)**?

### 2. Larger Code Comparison (§5): Model 1 (Explicit `&` Everywhere) vs. Model 2 (Default to Borrow `&` on Parameters)

You asked:
> *"It seems promising, but I'm not convinced one way or another yet. Show me some larger code comparison between the two models. You talk about a move keyword in model 2. What is that? That seems new."*

#### First: Why Mentioning `move` Was Unnecessary!
In my previous note, I wondered: *"If function parameters borrow by default in Model 2, what if a function actually wants to take ownership of a parameter instead of borrowing it?"*
**Wait—because you just locked in Pure Option 2 lifetimes and `.copy()`, you don't need a `move` keyword at all in Model 2!**
Here is why:
* Why does Rust ever move arguments into functions? Because in Rust, functions often take ownership of a parameter just to store it in a struct or return it.
* In Lowlight, you already decided that saving a parameter into a struct or returning it from a function **copies it via `.copy()`**!
* That means in **Model 2**, **every function parameter is either**:
  1. **Read-only (`param: T`)** — which automatically borrows (`&T`) for heap/struct types (or copies in a register for 8-byte scalars like `int`/`float`)!
  2. **Mutated in place (`param: &-T`)** — which requires `&-` in both the parameter list and the call site (`foo(&-x)`)!
There is **no third parameter mode** and **no `move` keyword**!

#### Side-by-Side Comparison on a Realistic 40-Line Program

Let's look at a realistic mini-program: an **Order Processing System** with `Item`, `Order`, helper functions (`calculate_subtotal`, `can_afford`, `format_receipt`), and a mutating function (`apply_discount`, `process_order`).

##### Model 1: Explicit `&` Required on Every Read-Only Parameter and Call Site (Current Spec)
In Model 1, if you forget `&` on a parameter `(order: Order)` or at a call site `calculate_subtotal(order)`, **`order` is moved and destroyed** on the first function call! So you must write `&` on almost every parameter and call:
```
define Item struct [
    name: string,
    price: float,
]

define Order struct [
    customer: string,
    items: [Item],
    discount: float,
]

// Must write `&Order` in signature, or calling this destroys the caller's Order!
bind calculate_subtotal = (order: &Order): float {
    let sum = 0.0
    for (item in order.items) {
        sum = sum + item.price
    }
    sum - order.discount
}

// Must write `&Order` and `&string` in signature:
bind format_receipt = (order: &Order, store_name: &string): string {
    // Must write `&order` when calling helper!
    bind total = calculate_subtotal(order)
    "[$store_name] Receipt for ${order.customer}: \$${total}"
}

// Mutating function: uses `&-Order`
bind add_item = (order: &-Order, name: &string, price: float) {
    order.items.push(Item[
        name: name.copy(), // `.copy()` creates an owned string for the struct
        price: price,
    ])
}

bind checkout = () {
    let store = "Lowlight Mart"
    let my_order = Order[customer: "Alice", items: [], discount: 5.0]

    // Must write `&-` for `my_order` AND `&` for `"Keyboard"` / `store`:
    add_item(&-my_order, &"Keyboard", 75.0)
    add_item(&-my_order, &"Mouse", 25.0)

    // Must write `&my_order` and `&store` at the call site, or they get moved/destroyed!
    bind receipt = format_receipt(&my_order, &store)
    bind final_total = calculate_subtotal(&my_order)
    print(receipt)
}
```

##### Model 2: Read-Only Borrow by Default + Explicit `&-` for Mutation + Explicit `.copy()` for Copying
Now look at the **exact same program** in Model 2.
* Read-only parameters (`order: Order`, `store_name: string`) are **automatically immutable borrows** under the hood—they never destroy the caller's variables, and you never have to clutter read-only calls with `&`!
* Only **mutations (`&-`)** and **copies (`.copy()`)** require visual markers:
```
define Item struct [
    name: string,
    price: float,
]

define Order struct [
    customer: string,
    items: [Item],
    discount: float,
]

// Read-only parameter `order: Order` is automatically a borrow (cannot be mutated, doesn't consume caller's Order):
bind calculate_subtotal = (order: Order): float {
    let sum = 0.0
    for (item in order.items) {
        sum = sum + item.price
    }
    sum - order.discount
}

// Read-only parameters `order: Order, store_name: string`:
bind format_receipt = (order: Order, store_name: string): string {
    bind total = calculate_subtotal(order)
    "[$store_name] Receipt for ${order.customer}: \$${total}"
}

// Mutating function: `&-Order` stands out immediately because ONLY mutations use `&-`!
bind add_item = (order: &-Order, name: string, price: float) {
    order.items.push(Item[
        name: name.copy(), // Explicit `.copy()` to store an owned copy inside `Item`!
        price: price,
    ])
}

bind checkout = () {
    let store = "Lowlight Mart"
    let my_order = Order[customer: "Alice", items: [], discount: 5.0]

    // Look at the call sites:
    // `&-my_order` jumps off the page as a mutation, while read-only args have zero `&` noise!
    add_item(&-my_order, "Keyboard", 75.0)
    add_item(&-my_order, "Mouse", 25.0)

    // Calling read-only functions never destroys `my_order` or `store`!
    bind receipt = format_receipt(my_order, store)
    bind final_total = calculate_subtotal(my_order)
    print(receipt)
}
```

#### What Happens on Local Variable Assignment (`let b = a`) in Model 2?
Wait—what if you write `let b = a` inside a function (assigning one variable to another, or putting a variable into a struct literal `Order[customer: name, items: my_items, ...]`):
* In **Model 2**, you have two ways to handle `let b = a`:
  * **Model 2A (Move on Assignment, Borrow on Function Call):**
    * Passing `my_order` to a read-only function parameter `(order: Order)` **borrows** it for the duration of the call (so calling functions never destroys your variables and never copies heap data).
    * Assigning an owned variable to another owned variable (`let b = a` or putting `my_items` into `Order[items: my_items]`) **moves** ownership into `b` / `Order` (zero copy!), or you write `a.copy()` if you want both `a` and `b` to have independent copies!
  * **Model 2B (Borrow on Assignment Too unless `.copy()` is called):**
    * `bind b = a` borrows `a`, while `let b = a.copy()` makes an independent copy.

Look at **Model 2A**:
1. Calling any normal function `foo(x)` **borrows `x` read-only** (zero copies, zero `&` clutter, and `x` is still valid after `foo(x)` returns!).
2. Calling a mutating function `foo(&-x)` requires **`&-` in the signature and `&-` at the call site**.
3. Making a deep copy requires **`.copy()`**.
4. Moving a freshly-built vector into a struct (`Order[items: my_items]`) moves ownership without copying!
*(And if someone still wants to write `&Order` or `&my_order` explicitly for documentation, we can allow redundant `&` just like in `if (&user?)`!)*

How does seeing **Model 1** vs. **Model 2 (2A)** side-by-side feel to you?

### 3. Enums (§8.2): Pros & Cons of Robust C-Style Enums vs. Tagged Unions (Payload Enums)

You asked:
> *"What are the pros and cons to having this more expanded definition of enums? I'm still not sold on having anything more than a robust version of C enums"*

This is a fundamental design choice. Let's compare **Robust C-Style Enums** vs. **Payload Enums (Tagged Unions)** honestly:

#### Option 1: Robust C-Style Enums Only (Pure Tags, No Per-Variant Struct Fields)
```
define Status enum [
    Pending,
    Active,
    Closed,
]

define Color enum [
    Red,
    Green,
    Blue,
]
```
* **What makes it a "Robust" C Enum (better than raw C):**
  * **Strictly typed:** Unlike C (where `Red` is just the integer `0` and you can accidentally pass a `Color` to a function expecting a `Status`), `Status` and `Color` are distinct types (`Status.Pending`, `Color.Red`).
  * **Can have methods & implement interfaces:** You can write `bind Status.to_string = (self: &Status): string ...`.
  * **Exhaustive `match`:** The compiler checks that `match (status)` handles `Pending`, `Active`, and `Closed`.
  * **Explicit integer conversion:** `int(Status.Pending)` converts to `0` when you want the underlying number.
* **Pros of Option 1:**
  * **Dead-simple mental model & C output:** Every `enum` is literally just a C `enum` (an integer tag, 4 or 8 bytes). Zero C `union` complexity, zero pattern-destructuring syntax (`when Circle[r]:` disappears!), and every variant is just `EnumName.VariantName`.
  * **Matches what most programmers think the word `enum` means** (an enumeration of named constants).
* **Cons of Option 1 (What you do instead when different variants have different data):**
  * If you are building something like a compiler AST or a shape renderer where a `Circle` has a `radius` and a `Rectangle` has `width` and `height`, you either:
    1. Use an **Interface** (`define Shape interface [ area: (&self): float ]`) implemented by separate `Circle` and `Rectangle` structs! (Wait—Lowlight *already* has interfaces in §8.3 that do this!)
    2. Or use a struct with an enum tag (`kind: ShapeKind`) or optional fields.

#### Option 2: Tagged Unions / Payload Enums (Current §8.2)
```
define Shape enum [
    Circle [ radius: float, ],
    Rectangle [ width: float, height: float, ],
    Point,
]
```
* **Pros of Option 2:**
  * Lets a single stack value hold one of several different struct layouts (`Circle` or `Rectangle`) without using an interface vtable, and lets `match` unpack the fields (`when Circle[r]:`).
  * Useful for **Error Handling** if errors are returned as a union of `[ Ok[val: T], Err[code: ErrorCode] ]`.
* **Cons of Option 2:**
  * Makes `enum` much more complex (variants look like structs inside an enum, require destructuring syntax in `match`, and in C must generate a struct + tag + union + custom drop logic if one variant holds a `string` and another holds an `int`).
  * Overlaps with **Interfaces (§8.3)**, which already solve polymorphism (`Circle` and `Rectangle` implementing `Shape`).

*(Note: There is also a middle path: make `enum` strictly **Option 1: Robust C-Style Enums** right now so `enum` is simple, clean, and rock-solid, and when we design **Error Handling** next, we can see if Error Handling needs anything more or has its own dedicated mechanism!)*
