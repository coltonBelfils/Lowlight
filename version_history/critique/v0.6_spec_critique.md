## 1. Your Two Questions on `for` Loops

### Question 1A: How Do the Compiler and User Know If a `for` Loop Is `T` or `?T`?
You asked:
> *"How is the compiler or the user supposed to know if the type is `T` or `?T`?"*

It follows one 100% deterministic visual rule (the exact same rule as `if` expressions!):

1. **Has an `else` clause $\rightarrow$ ALWAYS `T` (Non-Optional)**
   * Because the `else` clause provides a fallback value if the loop runs 0 times (or never breaks), a `for` loop with `else` **always** produces a `T`.
   * Therefore, the variable you assign it to **cannot** have a `?` suffix:
     ```
     // Has `else` -> type is `int` (`T`), assigned to `score` (no `?`):
     let score = for (round in 1..=5) {
         play_round(round)
     } else {
         0
     }
     ```
2. **No `else` clause $\rightarrow$ ALWAYS `?T` (Optional)**
   * Even if you write `for (i in 1..=5)`, a `for` loop **without** an `else` clause **always** has type `?T`.
   * Because of your mandatory `?` variable-naming rule (§6.2), any variable holding the result of an `else`-less `for` loop **must end with `?`**:
     ```
     // No `else` -> type is `?int` (`?T`), MUST be assigned to `score?` (with `?`):
     let score? = for (round in 1..=5) {
         play_round(round)
     }

     // COMPILE ERROR: `for` without `else` returns `?int`, so variable must be `score?` or loop must have `else`!
     let bad_score = for (round in 1..=5) {
         play_round(round)
     }
     ```

So both the human reader and the compiler know instantly at a glance:
* **`let x = for (...) { ... } else { ... }`** $\rightarrow$ `T`
* **`let x? = for (...) { ... }`** $\rightarrow$ `?T`

### Question 1B: Does `next <- val` Pass `val` to the Next Iteration's Expression?
You asked:
> *"Does `next <- val` pass `val` to the next iterations expression?"*

In Draft v0.5 as currently written, **no**—iterations don't automatically pass values to the next iteration. Wait, though: **your question exposes a really important point!**
Think about what happens if Iteration 1 does **not** pass its value to Iteration 2:
* If Iteration 1 runs `next <- val`, and then Iteration 2 runs, Iteration 1's `val` would just get overwritten by Iteration 2!
* The *only* time `next <- val` would ever matter without passing `val` to the next iteration is if Iteration 1 happened to be the **very last iteration** of the loop!

That gives us **two clear ways** to design how iterations interact with `next <-`:

#### Way 1: Iterations Are Independent, and "Last *Non-Skipped* Iteration Wins" (So `next <-` Never Needs a Value!)
If state across iterations is kept in normal `let` variables outside the loop (`let sum = 0`), then:
* **Bare `next <-` (no value)** skips the current iteration without updating the loop's result.
* If the final iteration of the loop is skipped via `next <-`, the loop simply evaluates to the **last iteration that actually produced a value** (or `else` / `none` if *every* iteration was skipped)!
  ```
  let sum = 0
  let total = for (x in [10, 20, -5]) {
      if (x < 0) next <- // Skips `-5`; Iteration 2's value (`30`) remains the winning value!
      sum = sum + x
      sum
  } else {
      0
  }
  // `total` is 30!
  ```
* Under Way 1, you never have to write `next <- sum` when skipping an iteration—bare `next <-` just skips the iteration and keeps the previous iteration's result intact!

#### Way 2: Each Iteration's Value IS Passed to the Next Iteration!
What if you *want* each iteration's expression (and `next <- val`) to pass its value directly into the next iteration?
How would the loop body refer to the value passed in from the previous iteration?
* For example, if the loop has an `else` initial/fallback value (or a named loop accumulator variable, or a built-in name like `prev` / `it`):
  ```
  // Suppose `prev` (or a named accumulator `sum = 0`) holds the previous iteration's value:
  let total = for (x in [10, 20, -5], sum = 0) {
      if (x < 0) next <- sum // Passes `sum` to the next iteration!
      sum + x                // Evaluates to `sum + x` and passes it to the next iteration!
  }
  ```
*(Notice that Way 2 is actually combining Design 2's accumulator with Design 3's "Last Iteration Wins"!)*

Between **Way 1** (bare `next <-` skips the iteration and keeps the previous iteration's result; cross-iteration state uses normal `let` variables) and **Way 2** (each iteration's expression / `next <- val` passes `val` into a loop variable for the next iteration), which one did you have in mind?

## 2. Model 2A vs. Model 2B: Why I Recommend Model 2A

You asked:
> *"Would you recomend 2A over 2B then? Let's go with Model 2, it's just if it should be 2A or 2B."*

**Yes, I strongly recommend Model 2A** (Move on local variable/struct assignment `let b = a`, Read-Only Borrow on function parameters `foo(a)`). Here is why **2A** works much better than **2B**:

1. **In 2A, constructing structs or reassigning variables has zero copy overhead:**
   Suppose you build a large vector `let items = [1, 2, 3, 4, 5]` and then construct an `Order` struct with it:
   ```
   let items = [1, 2, 3, 4, 5]
   let my_order = Order[customer: "Alice", items: items]
   ```
   * Under **Model 2A**, assigning `items` into `Order[items: items]` (or `let b = items`) **moves** ownership of the vector directly into `my_order` (0 bytes copied on the heap!). And if you *wanted* to keep using `items` separately, you write `items: items.copy()`.
   * Under **Model 2B** (where `let b = a` creates a borrow instead of moving), `my_order` cannot store a borrow (because structs only store owned data under Option 2!), so you would be forced to copy the entire vector just to put a local variable into a struct!
2. **In 2A, you never have to worry about local borrow lifetimes:**
   * In **2A**, every `let` or `bind` variable (`let x = ...`) is a normal, self-contained owned value, while **function parameters (`foo(x)`)**, **loop items (`for (x in list)`)**, and **optional unwraps (`if (user?)`)** borrow read-only by default (and use `&` for mutable borrows).
   * That makes the mental model effortless:
     * Passing `x` to a function `foo(x)` $\rightarrow$ **Borrows `x` read-only** (`x` is still yours after `foo(x)`!).
     * Passing `&x` to a function `foo(&x)` $\rightarrow$ **Borrows `x` mutably** (`foo` mutates `x` in place!).
     * Assigning `let b = a` or `Struct[field: a]` $\rightarrow$ **Moves `a` into `b`** (or copies for primitives like `int`).
     * Calling `a.copy()` $\rightarrow$ **Explicitly duplicates `a`** into a brand-new owned value.

If you agree with **Model 2A**, I will lock that into §5.1 of the spec!

### Parked Item A: Allowing vs. Forbidding `let Type.method` (§9)
Earlier you noted:
> *"I'm not fully dissuaded of allowing `let` for `type.method`. Lets come back to it in a bit"*

If we **allow** `let Point.length = (self: Point): float { ... }`:
* `bind Point.length = ...` compiles to a fixed static C function (`Point_length(pt)`).
* `let Point.length = ...` compiles to a global C closure variable (`Point_length`) that can be reassigned at runtime (`Point.length = new_func`), changing `.length()` for all `Point`s from that moment on!
* **One question if we allow `let Type.method`**: Should interface methods (like `Printable.to_string`) require `bind` methods, or can a `let Type.method` also satisfy an interface (updating the vtable or calling through the global pointer)?
* Would you like to **allow `let Type.method`** (compiling to a mutable global function/closure variable for that type), or keep methods `bind`-only?

### Parked Item B: Index + Element Iteration on Vectors (`for (i, item in my_list)`) (§11.2)
Now that `for` loops are settled:
* Maps support two loop variables: `for (k, v in my_map)` and `for (k, &v in my_map)`.
* Should vectors (`[T]`) and stack arrays (`[N: T]`) also support optional two-variable iteration:
  ```
  // Single variable -> iterates over elements:
  for (item in my_list) { ... }
  for (&item in my_list) { ... }

  // Two variables -> `i` is the `int` index (0, 1, 2...), `item` is the element:
  for (i, item in my_list) { ... }
  for (i, &item in my_list) { ... }
  ```
  This is super handy whenever you need both the index `i` and the element `item` without manually indexing `my_list[i]`.
