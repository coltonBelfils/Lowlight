#15. Compiler Architecture

The reference compiler is written in Go. One pipeline serves every command:

source files ─► lexer ─► parser ─► AST ─► semantic analysis ─► checked program
                                             (types, names,       │
                                              ownership)          ▼
                     executable ◄─ C compiler / linker ◄─ backend ◄─ MIR (lowering)
                                                         (LLVM IR or C11)
StagePackageResponsibility
Lexinginternal/lexer, internal/tokentokens, semicolon insertion, ?/! name suffixes, <- recognition, string interpolation
Parsinginternal/parser, internal/asta syntax tree for each file; doc comments
Semantic analysisinternal/sema, internal/typesname resolution across a package, type checking, monomorphization, ownership and borrow checking, exhaustiveness
Loweringinternal/ira mid-level IR (MIR) in which every type is concrete, and every temporary, move, and destruction is explicit
Code generationinternal/codegenLLVM IR (default) or ISO C11 from MIR, plus a small C runtime
Driverinternal/driverpackages, caching, invoking clang/cc, running programs and tests
Toolsinternal/format, internal/docgen, internal/lsp, internal/manifestformatter, documentation, language server, manifests and dependencies

Compilation units. A package is all .ll files in one directory, minus test files outside lowlight test and files excluded by platform suffixes (§4.6). Packages form a directed acyclic graph through their imports; inside a package, declarations may refer to each other in any order and recursively.

Two-phase builds. When building a project, each non-generic package is compiled to its own cached object file, keyed by a hash of its sources, the compiler version, and its dependencies' interfaces. Generic instantiations and interface vtables, which depend on how packages are used together, go into one shared unit compiled last. --no-incremental disables the cache. This is an optimization only; the output must be the same.
